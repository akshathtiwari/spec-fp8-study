## FIELD 2 — "Proposal to improve performance"

```
Not a proposal so much as a measurement suggestion: speculative-decoding
throughput on this stack is boot-dependent to a degree that a single-boot
benchmark cannot see. On vLLM 0.29.0 / L4, twelve boots of a byte-identical
configuration gave a coefficient of variation of 13.92% in one container and
3.73% in another. Anything comparing speculative configurations from one boot
each is, on this stack, partly measuring which boot it got.

0.30.0 looks much better on this axis (0.99% and 1.61% across two containers
on different physical cards), so this may already be resolved. I am reporting
it mainly because the mechanism is not what I assumed, and because the
measurement protocol seems worth having on record either way.
```

## FIELD 3 — "Report of performance regression"

```
Reporting this because 0.30.0 appears to resolve it, and the obvious
explanation turns out to be wrong, so something else changed and I would like
to know what.

**Setup.** Qwen3-4B target, `z-lab/Qwen3-4B-DFlash-b16` drafter, 5 speculative
tokens, bf16 weights, `--kv-cache-dtype auto`, FlashInfer pinned. GSM8K,
concurrency 1, one fixed prompt set replayed on every boot. 12 boots per arm
inside a single container, one physical GPU per session with the UUID
recorded. The harness speaks HTTP only and never imports vLLM.

Throughput at concurrency 1, output tokens/s:

| card | engine | session | default | `--enforce-eager` | ratio | default CV |
|---|---|---|---|---|---|---|
| L4 (SM89) | 0.29.0 | A | 39.2 | 80.5 | **0.487** | **13.92%** |
| L4 (SM89) | 0.29.0 | B | 61.2 | 79.7 | **0.768** | **3.73%** |
| L4 (SM89) | 0.30.0 | C | 82.8 | 81.6 | **1.014** | 0.99% |
| L4 (SM89) | 0.30.0 | D | 78.2 | 77.0 | **1.017** | 1.61% |
| A10 (SM86) | 0.29.0 | E | 132.6 | 138.3 | 0.959 | 2.08% |

Each ratio is the default arm divided by the eager arm measured in the *same*
container, so session and card effects cancel. On 0.29.0 / L4 the CUDA-graph
path runs at 49% and 77% of the eager path. On 0.30.0 it reaches parity.
Acceptance length is flat throughout (tau 4.11-4.15), so this is a throughput
effect rather than a change in what the drafter gets accepted.
```

## FIELD 4 — "Misc discussion on performance"

```
Two observations and a question.

**1. The CUDA-graph fallback still fires on 0.30.0.** I assumed the
improvement was the speculative path gaining full graphs. It is not. The
warning is byte-identical on both versions, and capture proceeds under
PIECEWISE in each:

CUDAGraphMode.FULL_AND_PIECEWISE is not supported with spec-decode for
attention backend FlashInferBackend (support:
AttentionCGSupport.UNIFORM_SINGLE_TOKEN_DECODE); setting cudagraph_mode=PIECEWISE

Backend selection is unchanged too: both versions log FLASHINFER for the
target and FLASH_ATTN for the second selection. So neither graph mode nor
backend choice explains the difference.

**2. On 0.29.0 the dispersion magnitude is itself not reproducible.** Two
twelve-boot measurements of the identical configuration gave 13.92% and 3.73%,
with means 39.2 and 61.2 tok/s. The effect is present in both; its size is not
a property of the configuration. The eager arm is stable across every session
measured (80.5, 79.7, 81.6, 77.0, 138.3 - within a few percent per card),
which is what makes it usable as a control.

**The question:** what changed between 0.29.0 and 0.30.0 on this path, given
the fallback and the backend selection are the same in both? If a specific PR
is responsible I would like to cite it correctly rather than guess. I looked
at #53867, #51700, #54646 and #52228 and could not attribute it from the
release notes alone.

**Possibly relevant:** the effect is much weaker on an A10 (ratio 0.959)
than on an L4 (0.487 and 0.768) at the same engine version. The A10 has 24 GiB
against the L4's 22.03 GiB usable, and this configuration sits close enough to
the memory ceiling that `--enforce-eager` alone decides whether an fp8_e4m3-KV
variant boots at all. So capacity pressure may matter here more than
architecture. I have not separated the two.

**Reproduction.** Harness, raw append-only records, the analysis scripts and
the engine logs are at https://github.com/akshathtiwari/spec-fp8-study
(archived: https://doi.org/10.5281/zenodo.23033168). The boot-variance runs
are one command each; per-session numbers regenerate from the stored records.

Happy to run further configurations if a specific one would help - the full
sweep is a couple of GPU-hours.
```
